## 1. Обзор проекта

**Signal Arena** — обучающая игра о навыках анализа и торговли на криптовалютных
биржах. Сложный теоретический материал подаётся через игровой опыт, соревнование
и визуальный язык арены.

### Что утверждено (обязательно к исполнению)

| Компонент | Технология | Статус |
|---|---|---|
| Игровой клиент | **Phaser 4** + TypeScript + Vite | ✅ `phaser/` |
| Сервер | **Fastify** + SQLite (sql.js) + Drizzle + Zod + WS | ✅ `backend/` |
| Текст игры | **«Панк-таблоидная криптосатира»** | ✅ `style-tone.txt` |
| Детерминизм | seedrandom + scenario-gen | ✅ планируется |
| Менеджер состояния | **Zustand** (без React) | ✅ планируется |

### Что НЕ утверждено (концептуально, необязательно)

Всё, что не перечислено в разделе «Что утверждено» выше, а также:
- вся папка `concepts/` — идеи от разных людей, разные движки, возможны баги
- вся папка `brand_identity_main_idea/` — фирменный стиль не придуман
- вся папка `game_characters/` — арт-ассеты в статусе референсов

Подробнее в `README.md`.

## 2. Технический стек

### Утверждённый стек (обязателен)

```
Фронтенд:  Phaser 4 + TypeScript + Vite + Zustand
Бэкенд:    Fastify + SQLite (sql.js) + Drizzle ORM + Zod + WebSocket
Текст:     style-tone.txt (правила тона)
Генерация: seedrandom + scenario-gen (детерминированный)
Тесты:     Vitest (unit) + Playwright (e2e)
Сборка:    Vite (target: es2020)
PWA:       vite-plugin-pwa
```

### Предложенный, но не проверенный стек

Ранее был предложен следующий набор. Оценка где критично, где нет:

| Технология | Критично? | Примечание |
|---|---|---|
| **Phaser 3 → 4** | ✅ Критично | Уже на 4.2.1. Не использовать 3. |
| **rexUI** | ⚠️ Не критично | Плагин для UI внутри сцены. Нужно проверить совместимость с Phaser 4. Можно обойтись без него — писать UI на чистом Graphics. |
| **Custom CandleChart on Graphics** | ✅ Критично | График должен быть частью игрового канваса, а не iframe/widget. Lightweight-charts не подходит — это веб-виджет. |
| **Zustand** | ✅ Критично | Единственный правильный выбор для сториб в Phaser (без React). |
| **seedrandom + scenario-gen** | ✅ Критично | Детерминизм — утвержденное требование. |
| **Fastify + SQLite + Drizzle + Zod + WS** | ✅ Критично | Уже в `backend/`. |
| **Phaser Sound** | ⚠️ Не критично | Часть Phaser, используется по необходимости. |
| **vite-plugin-pwa** | ⚠️ Не критично | Планируется, но не обязательна для MVP. |
| **Vitest** | ✅ Критично | Уже настроен в `phaser/vitest.config.ts`. |
| **Playwright** | ⚠️ Не критично | E2E-тесты — после MVP. |

## 3. Как запустить

```bash

cd phaser
npm i
npm run dev           # → http://localhost:3000

# Бэкенд (сервер + CRM)
cd backend

npm run start         # → http://localhost:8080
```

## 6. Конвенции кода

- **Язык кода**: TypeScript во фронтенде, TypeScript в бэкенде
- **Стиль именования**: `camelCase` для переменных, `PascalCase` для классов
- **Структура Phaser**: один класс сцены на файле, сцены в `phaser/src/scenes/`
- **Импорты**: относительные, без `src/`-алиасов если можно обойтись
- **Коммиты**: не делай коммиты без прямого запроса. Описание коммита — кратко и по делу.
- **Задачи ИИ**: не задаю вопросы в конце ответа, сразу делаю следующий шаг.
- **Язык**: в UI и описаниях — **простыми словами** (см. `docs/glossary.md`).
  - Термины индустрии (FOMO, loss aversion, leverage) — **оставлять как есть**
  - Проектные термины (атомы → навыки, свиток ошибок → журнал ошибок) — **упрощать**
  - Атомы → всегда пиши «навык» или «умение» в UI и описаниях

## 7. Стиль текста

Все тексты игры — в стиле **«панк-таблоидная криптосатира»**:

- Кратко, драматично, сухо
- Криптожаргон → социальная сатира
- Формула: `[Драматичный заголовок] + [простая правда] + [неприятный/смешной вывод]`
- Игрок — не герой, а участник системы
- Детали — в `style-tone.txt`

Имена сущностей (персонажи, враги) **не переводятся** — остаются на английском
терминах (Leverage Goblin, FOMO Wraith и др.). Остальной интерфейс локализуется.

утверждённом стеке. **Не порти существующие прототипы.**

## 12. Протокол разработки

Соблюдай **фазовый план** из `DEVGUIDE.md`. Разработка идёт по секциям:

0. Аудит → 1. Foundation → 2. Core Loop (L0–20) → 3. Content →
4. UI & Assets → 5. Motion & Audio → 6. QA gate → 7. Backend →
8. Scale L21–99 → 9. Future GameFi

- Перейти к следующей секции можно **только после QA/playtest gate** текущей
- **Помечай статус** задач в `DEVGUIDE.md` при начале и завершении
- **Не делай** то, что отмечено как «🟢 Отложить» или «🛑 БЛОКИРОВАНО»
- Спрашивай, если задача выходит за рамки текущей секции

**GameFi, токены, NFT, звук** — строго после финального релиза и QA gate.

Тестирование на каждой секции — обязательный критерий перехода к следующей.

## 13. Эталонные источники (только для вдохновения)

Следующие внешние папки и файлы содержат эталонные документы — **никогда не
копировать код**. Только изучать идеи, переписывать на Phaser 4 + Fastify:

- `Downloads/signal-arena-all-prompts-v1.2.zip` — фазовый план (01→09),
  master prompt, phaser shell, UI system, motion catalog, backend contracts
- `Downloads/signal-arena-design-system.zip` — 12 HTML-скринов, design tokens,
  component contracts (mobile-first 390px, hit area ≥44×44px, reduced motion)
- `Downloads/motion_interaction_catalog_for_all_prompts.md` — каталог
  микровзаимодействий и анимаций (70 событий, 3 MVP-группы)
- `Downloads/arenaui-main 3/new.txt` — детальное ТЗ (Часть 1)
- `concepts/arenaui-main 3/COMPONENT_CONTRACTS.md` — UI контракты

**Design system важен:** он описывает **canonical constraints**, которые не
меняются. Например: "Four equal navigation items" (Arena, Academy, Collection, More),
"No HP, FOMO meter, pay-to-win". Это наш устав — не нарушать.

## 14. Статус текущего кода

Код в `phaser/src/` — **фундамент** (main.ts, gameConfig.ts, BootScene.ts, UI-примитивы, rng.ts).

Бэкенд (`backend/`) содержит реализацию от предыдущего цикла — она сохранена
как справочник, но не используется. План бэкенда — в `docs/specs/BACKEND_PLAN.md`.
Перед выполнением задачи всегда проверяй `DEVGUIDE.md` и не вводи новые
функции вне текущей секции.

## 15. Как действовать с ограничениями окружения

**Принцип:** следуй инструкциям строго. Не придумывай обходные пути.

| Ситуация | Действие |
|---|---|
| Пакет/зависимость недоступна | **Не подменяй** другим. Запиши `// TODO: <что> недоступно в среде, требует <замена>` |
| Инструмент не установлен | **Не обходи** аналогом. Сообщи в комментарии, иди к следующей задаче |
| Инструкция противоречит стеку | Действуй по инструкции. **Не оптимизируй самостоятельно** |
| Не хватает данных/ассетов | **Не генерируй вымышленные**. Используй fallback или оставь TODO |
| Баг в существующем коде | **Не чини без указания**. Зафиксируй, продолжай по плану |

**Худший исход:** AI самостоятельно выбирает упрощение или обходной путь.
**Лучший исход:** AI делает, что может, фиксирует недоступное, движется дальше.
